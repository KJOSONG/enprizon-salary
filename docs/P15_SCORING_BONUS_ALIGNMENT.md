## 一、三层模型数值化（以手册为准）

### ① 产量层 — 奖金池生成

```
总池 = max((当月 NICKEL(H) 车次 − 600), 0) × 20,000
半池 = 总池 × 50%
```

- **仅 NICKEL(H)** 高镍产量（车次）参与。NICKEL(L)、MAWE 均不参与。
- NICKEL(H) < 600 车次 → 总池 = 0（当月无奖金池，全员固定工资）。
- 两班半池互不牵连（各拿总池的 50%）。
- 例：月总产量 3000、镍产量 1000 → 总池 = (1000−600)×20,000 = 8,000,000，半池 = 4,000,000。

**数据源**：井下采集 `collection_submissions`（form_type='underground'）payload 的 `day.nh + night.nh` 汇总当月。

### ② 客观层 — 发放比例

```
S = R1 × 70% + R2 × 30%
R1 = 实际出渣量 ÷ 计划出渣量（不封顶，可超 100）
R2 = 有效作业时间 ÷ 在井总时长（上限 100）
月度 S = 全月当日 S 的算术平均值
```

- 计划出渣量 = 0 时，R1 不参与，当日 S = R2 × 30%。
- R1 的**实际出渣量** = 当日井下总产量（nh + nl + mw，车次），由采集数据自动汇总。
- **计划出渣量**由中方管理每日在客观录入表手工设定。

**发放比例阶梯（90/80/70/60 五档）**：

| 月度 S | 实发比例 |
|--------|----------|
| ≥90 | 100% |
| 80–89 | 95% |
| 70–79 | 90% |
| 60–69 | 80% |
| <60 | 70%（保底） |

```
各班实际奖金池 = 半池 × 实发比例
```

### ③ 主观层 — 个人份额

```
维度均值（1–5）→ 去最高最低各 1 票 → 均值
行为分 = (均值 − 1) ÷ 4 × 100
系数：≥85 → 1.2 / 70–84 → 1.0 / 60–69 → 0.8 / <60 → 0.5
管理 1.5 票：最终行为分 = (工友分×有效票数 + 管理分×1.5) ÷ (票数 + 1.5)
```

```
个人奖金 = 各班实际奖金池 × (个人系数 ÷ Σ本班全部系数)
Σ 个人奖金 = 班实际池（总额守恒）
```

### 防串通三闸（前端面板展示，阈值可调）

1. 零方差复核：行为分极差 ≤ 8 → 触发人工复核
2. 最高档上限：系数 ≥ 1.1 人数 ≤ 30%（豁免：全班行为分 ≥ 85 且管理偏离 < 10）
3. 管理锚偏离：工友分与管理分偏离 > 15 → 触发复核

可配置项：`mgmt_vote_weight=1.5` / `mgmt_deviation_threshold=15` / `zero_variance_threshold=8` / `max_tier_ratio=0.3`

## 三、开发设计要点

### 产量层
- 新增函数 `compute_scoring_pool(shift_data)`（或等价），汇总当日 `day_prod.nh + night_prod.nh` → 月 NICKEL(H) 车次 → 总池/半池。
- 600 门槛、20,000 单价：建议进 `settings`（沿用 pricing 模式，`/config` 可改），默认值与手册一致。
- `_get_scoring_bonus` 半池改由该函数计算。

### 奖金计算（`_get_scoring_bonus` 重写）
- 读新表 `scoring_card_entries`（旧表回退，仿 `app.py:2164-2181` summary 逻辑）。
- **抽公共函数与 summary 复用**：分票（工友/管理）→ **去极值（剔除最高/最低各 1 票，票数<3 不剔）** → 管理 1.5 票加权 → final_behavior → 系数，两端共用，杜绝"展示一个数、算钱另一个数"。
- **匿名原则（2026-08-13 用户决策）**：评分匿名，**不记录评分人（operator_id 不使用）**，只区分工友票/管理票；自评票不显式剔除，靠去极值（剔最高最低各 1 票）兜底。
- 修正 sum_coef：遍历班内每个成员**各自的系数**求和。
- 三闸豁免：全班 final_behavior≥85 且 max(|peer−mgmt|)<10 时，最高档 30% 上限失效。
- 月份过滤：`scoring_card_entries` 无 month 列 → **加 `month` 列 + 重建 UNIQUE**（仿 `scoring_cards` P10-fix，`core/database.py:333-359`），8 月按 `substr(submitted_at,1,7)` 回填。
- 需要当月 NICKEL(H) 车次：`calculate_all` 内从 `main_data['shift_production']` 汇总（app.py `_merge_collection_to_main_data` 已建成 day_prod/night_prod 含 `NICKEL（H）`）。

### 客观层录入规则（2026-08-13 用户决策）
- **实际出渣量（actual_output）**：**强制自动** = 当日井下采集全部产量（NH + NL + MAWE 之和），**不允许手动填写**。前端客观录入表单只读自动填充。
- **计划出渣量（planned_output）**：管理填写；**未填 → 提醒手动补录，该日不计入发放**（无计划出渣量的日子不参与 S 汇总）。
- **在井总时长（total_hours）**：默认 10 小时，可修改。
- **有效作业时间（effective_hours）**：同理计划出渣量逻辑——未填提醒补录；默认可给提示值由管理修改。
- **已提交的客观录入可被修改**（编辑已存在记录）。
- 后端提供 `/api/objective/suggest?date=` 返回当日总产量供自动带出（与计薪同源 `APP_STATE['main_data']`）。

## 四、双场景验证方案

测试方式：`_work/` 下验证脚本构造 synthetic `main_data` 调用 `calculate_all`（**不污染本地 kilwa.db**），同时跑 `p14_full_verify.py` 回归。

### 场景 A：无池（8 月现网数据）
- 实测 NICKEL(H) = 167 车次（11 天）< 600
- 断言：总池 = 0、个人奖金 = 0；scoring 模式井下工人走月薪轨道，无报错。

### 场景 B：有池（构造测试月份）
- 构造 NICKEL(H) = 1200 车次 → 总池 = (1200−600)×20,000 = 12,000,000，半池 = 6,000,000
- 给定客观层月度 S（如 85.1 → 95% 档）→ 班实际池 = 6,000,000×0.95 = 5,700,000
- 给定 7 人系数（1.2/1.0/1.0/1.0/0.8/0.5/1.2，ΣC=6.7）→ 逐人断言：
  - W1: 5,700,000×1.2/6.7 = 1,020,896（手册示例精确复算）
  - 总额守恒：Σ 个人奖金 = 5,700,000

### 回归
- 日工资明细 vs 薪资总表逐人逐日一致
- 双路径核对 0 偏差
- piecework 模式不受影响
